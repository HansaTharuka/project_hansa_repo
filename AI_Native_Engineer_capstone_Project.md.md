## 3. Problem Statement & Expected Solution

### 3.1 Problem

A wealth management firm wants to launch self-service robo-advisory for retail investors. You build customer risk profiling, rule-driven portfolio recommendation, goal tracking, and rebalancing nudges - under one constraint: no manual coding. Recommendation logic is deterministic and rule-based (not ML). Every line of production code must be generated by Claude Code agents under your supervision.

### 3.2 Your Role

AI-Native Engineer - architect, supervisor, and quality gatekeeper. You write specifications, configure agents, install guardrails, and review pull requests. You do not write production code by hand.

### 3.3 Expected Solution

A working platform delivered as a Git repository that demonstrates:

* A complete AI-native engineering substrate built on the Claude Harness Engine plugin foundation, extended with wealth-advisory-specific specs, agents, skills, hooks, commands, and MCP integration.

* A functional robo-advisory platform built end-to-end by Claude Code agents - covering risk profiling, allocation recommendation, drift detection, and rebalancing - with no hand-written production code.

* An evidence trail (PRs, agent logs, post-mortems, sprint contracts) proving the work was agent-led.

### 3.4 Applicable Rules

* **No-Hand-Coding Rule.** All production code, tests, and migrations must be generated by Claude Code agents. Hand-edits are limited to specs, CLAUDE.md, agent definitions, hooks, skills, and other substrate files.

* **Spec-Is-Truth Rule.** Whenever a spec and code disagree, the spec wins. Update the spec deliberately and regenerate the code.

* **PR-Only Merge Rule.** No direct commits to main. All changes flow through agent-reviewed pull requests.

* **Synthetic-Data Rule.** Use only dummy data. Do not use Virtusa confidential or customer-sensitive data for this project.

## 5. Acceptance Criteria & Non-Functional Requirements

### 5.1 Functional Acceptance Criteria

| ID | Criterion |

|---|---|

| **AC-01** | Customer can complete a risk-profile questionnaire of at least 6 questions; a deterministic scoring rule assigns a risk band (CONSERVATIVE / MODERATE / AGGRESSIVE) |

| **AC-02** | Risk band determines a recommended asset allocation per a versioned template; allocation percentages always sum to 100 |

| **AC-03** | Customer can create financial goals with target_amount, target_date, and priority; multiple goals per customer are supported |

| **AC-04** | Portfolio-recommendation engine returns an allocation that maps to the customer's risk band and goal horizon; output is deterministic given the same inputs |

| **AC-05** | Customer holdings track current value per asset class; allocation drift = abs(current% - target%) is calculated for each asset class |

| **AC-06** | Rebalancing recommendation is generated when any asset class's drift exceeds the configured threshold (e.g., 5%) |

| **AC-07** | Rebalancing engine proposes BUY / SELL quantities with a recommendation ID; customer can accept or dismiss with audit |

| **AC-08** | Goal progress is reported as percent_complete = current_goal_value / target_amount; updated on each daily NAV refresh |

| **AC-09** | Advisor can override a customer's risk band with reason and supporting note; the override is audited with actor and timestamp |

| **AC-10** | Risk-band rules and asset-allocation templates are versioned; published versions are immutable; in-flight customers continue on the version active at the time of their recommendation |

*Note: Each AC must have at least one test referencing its AC-NN identifier.*

### 5.2 Non-Functional Requirements

| ID | Requirement |

|---|---|

| **NFR-01** | Portfolio values, allocation percentages, and drift are computed in fixed-point - never floating-point |

| **NFR-02** | Risk-band assignments, recommendations, rebalancing actions, and overrides are append-only |

| **NFR-03** | Customer PII and financial-position data are never written to logs |

| **NFR-04** | Authentication boundary at controller layer; customer / advisor / admin roles are separated |

| **NFR-05** | Database, policy, and template migrations are append-only |

| **NFR-06** | Structured JSON logs with request correlation IDs |

| **NFR-07** | Health endpoint returns 200 within 1 second of a successful startup |

| **NFR-08** | Architecture rules enforced as tests - allocation percentages must sum to 100; published templates cannot be mutated; risk-band reassignment requires an override audit record |

## 6. Functional Scope

### 6.1 Customer / End-User Functionality (User Journeys)

* **Risk Profile:** Complete the risk-profile questionnaire; see assigned risk band.

* **Goals:** Set financial goals (retirement, education, home) with target amount and date.

* **Recommendation:** View recommended asset allocation per risk band and goal horizon.

* **Holdings:** View current holdings and allocation drift per asset class.

* **Rebalance:** Receive rebalancing recommendations when drift exceeds threshold; accept or dismiss.

### 6.2 Internal & System Functionality

* **Advisor Workbench:** Customer portfolio view, override risk band with reason, log manual recommendation.

* **Asset Price Feed (stub):** Daily NAV updates per asset class on a configurable schedule.

* **Rebalancing Engine:** Detect drift > threshold, propose BUY / SELL quantities, generate stubbed orders.

* **Goal Tracker:** Compute and snapshot progress per goal on each NAV refresh.

* **Admin:** Edit risk-band rules and questionnaire scoring; manage asset-class master and versioned allocation templates.

### 6.3 Out of Scope

You do not need to build:

* Real exchange or brokerage integration

* Real-time market data (stubbed daily NAV only)

* Multi-currency or FX

* Tax-loss harvesting and tax optimization

* Real KYC document workflow (use a stub flag)

* Machine-learning-based recommendation (rule-based only)

* Production deployment, secret management, multi-region

## 7. AI-Native Implementation Expectations

On top of that foundation, your repository must add the project-specific substrate listed in this section. The rubric scores the final repository - both Harness-supplied and learner-added artifacts contribute, but the thresholds below are calibrated so that learners who only install Harness without customizing for the project domain will not meet them.
